# Deployment target: Render, plus bearer-token auth on the MCP endpoint

**Date:** 2026-09-21

Two decisions made together, since they're connected (choosing HTTP transport made both necessary):

**Hosting: Render.** Its free/hobby tier is straightforward for a small FastAPI app and deploys directly from GitHub — a good fit for something a Tech Lead needs to open with minimal friction. Trade-off knowingly accepted: Render's free tier has an **ephemeral filesystem** — `spotify_mcp.db` would be wiped on every restart/redeploy, losing the stored Spotify token. This was anticipated back in [entry 04](04-token-storage-database.md) ("easy path to Postgres later"); the actual migration to Render's free Postgres instance is still pending, to be done as part of the deployment work itself, not before.

**MCP endpoint auth: a bearer token.** Flagged as an open question back in [entry 01](01-mcp-transport-streamable-http.md) — HTTP transport makes the server network-reachable, so once it's on a real public URL, anyone could call `/mcp-server/*`. Implemented as a small ASGI middleware (`src/spotify_mcp/mcp/auth.py`, `BearerTokenMiddleware`) wrapping only the mounted MCP sub-app: every HTTP request must carry `Authorization: Bearer <MCP_BEARER_TOKEN>` or gets a `401`. Deliberately **not** applied to `/auth/*` — those routes are reached by browser redirects (the user opening `/auth/login`, Spotify redirecting to `/auth/callback`), which can't easily carry a custom header, and their security already comes from Spotify's own login screen. `/health` also stays open, since it carries no sensitive data and is useful for host health checks. Token compared with `secrets.compare_digest` to avoid timing attacks.

Verified: a request to `/mcp-server/mcp` without the header gets `401`; a real MCP client with the token in an `Authorization` header connects, lists tools, and calls `ping` successfully; `/health` still works with no token.

**Testing gotcha found while writing `tests/test_mcp_auth.py`**: `mcp_server` (in `mcp/server.py`) is a module-level singleton, and its `StreamableHTTPSessionManager.run()` — entered once via our FastAPI `lifespan` — raises `RuntimeError: ... can only be called once per instance` if entered a second time. Not a production bug (the real app's lifespan is entered exactly once, for the life of the process), but it means every test that does `TestClient(spotify_mcp.main.app)` in the same pytest run shares that one singleton, so only the *first* such test can ever successfully enter it — a second one fails immediately at startup. `tests/test_health.py` already used the real app once; adding a second full-app `TestClient` usage in `test_mcp_auth.py` broke both. Fixed by testing `BearerTokenMiddleware` in isolation — wrapping a minimal standalone Starlette app instead of the real one — since the 401/200 behavior doesn't actually depend on the real MCP server underneath. General rule going forward: **at most one test in the whole suite exercises the real `spotify_mcp.main.app` through its full lifespan**; anything else gets tested against the smallest app that reproduces the behavior.
