# Shuffle/repeat/seek, Liked Songs, and friendly playback/API error messages

**Date:** 2026-09-22

Three small playback-control tools plus a new domain (the user's Liked Songs library), all decided together as "the rest of the cool stuff" from an earlier discussion.

**Shuffle, repeat, seek** (`shuffle`, `repeat_mode`, `seek`): no new scope needed (`user-modify-playback-state` already covers them). First attempt at testing hit `404 "Player command failed: No active device found"` — expected, no device was playing at the time; retried once the user had Spotify actively playing and all three worked (`PUT /me/player/shuffle`, `/repeat`, `/seek`, all `200`).

That "no active device" response was the trigger for a real gap: **none of the playback tools had ever handled a Spotify API error gracefully** — a failed call would bubble up as a raw `httpx.HTTPStatusError`, and over MCP that surfaces as an ugly unhandled-exception dump instead of a message the model (or the user) can read. Fixed by adding `SpotifyPlaybackError` (`spotify/client.py`), which extracts Spotify's own `error.message` from the response body, and wiring it into all six existing playback tools (`pause`, `resume`, `skip_next`, `skip_previous`, `set_playback_volume`, `queue_track`) as well as the three new ones — not just the new tools, since the gap was pre-existing and this was the natural moment to close it everywhere at once.

**Liked Songs** (`liked_songs`, `like_tracks`, `unlike_tracks`): needed two new scopes, `user-library-read` and `user-library-modify`, so the user re-logged in once (`spotify-mcp login`) — verified independently afterward by reading the fresh scope string out of `spotify_mcp.db`, not just taking the login command's own "success" exit code at face value.

`liked_songs` (`GET /me/tracks`) worked immediately with real data. `like_tracks`/`unlike_tracks` (`PUT`/`DELETE /me/tracks`) did not: a bare `403 "Forbidden"`, tested with both query-param and JSON-body id formats to rule out a body-shape issue like the ones found for playlists — same result either way. This is the same signature as the two earlier Development-Mode restrictions ([entry 13](13-recommendation-endpoints-restricted.md), [entry 23](23-find-playlists-and-playlist-track-access-limit.md)): a plain `Forbidden` with no scope-related message means the app itself isn't allowed to call the endpoint, not that a permission is missing — the token *does* carry `user-library-modify`. Spotify gates *writing* to a user's Liked Songs behind "Extended Quota Mode" approval, while *reading* it is open.

Added a second, more general error type for this — `SpotifyAPIError` (distinct from `SpotifyPlaybackError`, since it's not playback-specific) — and wired it into `like_tracks`/`unlike_tracks` so a real 403 shows as `"Spotify API error: Forbidden"` instead of crashing the tool call, confirmed live. Kept both tools in the codebase despite being non-functional under this app's current Development Mode tier: the implementation is correct per the documented API, and would start working immediately if the app were ever granted Extended Quota Mode — removing correct code because of an environment-specific restriction would just be throwing away working functionality. Their docstrings say this plainly, so the model doesn't present a failure as unexplained.
